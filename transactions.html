    Transactions

    Transactions and the UTXO visualizer

    Sending DUST-20 is building a Bitcoin transaction whose output layout produces the result you intended. Change the layout below and watch which units survive.

    The rule that matters

    A unit survives a spend only when its whole block of unit_sats satoshis lands inside a single supported output. Everything else is burned — silently, in a transaction Bitcoin confirms normally.

    input_units = surviving_units + burned_units There is no third outcome. Units are never partially moved, rounded, or held in reserve.

    Three things must be true of a safe send:

    • The receiver's output is large enough to hold the units you are sending, positioned so each unit fits whole.
    • A colored change output exists for every unit you are keeping, unless you are sending the entire allocation.
    • A cardinal input funds the fee, so no colored satoshi is paid to a miner.
    !

    Missing colored change is not a formatting problem

    If you spend an allocation of 91 units and only create an output for 10, the other 81 are destroyed. There is no recovery, no mempool warning and no error from your wallet. Confirm the change output exists before you approve anything.

    Cases and failure modes

    Constructions that work

    CaseWhat to buildWhy it holds
    Full send One colored output sized to the whole allocation, plus a cardinal input for the fee. Nothing remains, so no colored change is needed. The review should still state plainly that everything is being sent.
    Partial send A colored output for the receiver, a colored change output for the remainder, a cardinal input for the fee. The colored range is fully covered by supported outputs, so every unit lands whole.
    Merge Several colored inputs of the same ticker and unit size, combined into one output large enough for all of them. Each contributing unit still lands whole inside the destination. Allocations of different tickers keep separate identities by offset.
    Multiple recipients One colored output per recipient, in the order you intend, then colored change. Ordinal flow fills outputs in order, so the first output takes the first units.

    Constructions that destroy units

    FailureWhat happensHow to avoid it
    Missing colored change Units beyond the receiver's share fall into ordinary outputs or the fee and are destroyed. Always create a colored change output when you are sending less than the full allocation.
    Fee taken from backing The colored range extends past the last output. Those satoshis go to the miner and their units are burned. Add a cardinal input sized to cover the fee. Never shrink a colored output to make room.
    Output too small A colored output that cannot hold a whole unit receives nothing; the units that would have landed there are burned. Size every colored output to at least units × unit_sats.
    Split across a boundary A unit straddling two outputs does not survive in either. Align output sizes to whole multiples of the unit size wherever colored satoshis flow.
    Unsupported output Units reaching an output the indexer cannot attribute to an address are burned. Send colored value only to standard, addressable outputs.
    Reordered outputs Units land in whichever output occupies their position in the satoshi range — possibly the ordinary change output. Treat output order as part of the transaction's meaning, and test your builder's exact ordering.
    Stale input The selected output was already spent, so the transaction is invalid or spends something you did not intend. Revalidate every outpoint immediately before building, not at page load.

    Situations that are genuinely ambiguous

    Some questions have no authoritative answer. They are documented as open rather than resolved by guesswork — see the open questions for the full list and the safe posture for each.

    • Replacement transactions. An RBF replacement can have a different output layout, so it can burn units the original preserved. Always re-derive allocation from the transaction that actually confirmed.
    • Unconfirmed state. Mempool coverage is partial, so pending DUST-20 state is not a safe basis for an irreversible decision.
    • Cross-implementation agreement. Most transfer behaviour is settled by one production implementation rather than a multi-party specification. Test against the indexer your users will actually see.

    DUST

    DUST-20

    DUST-20 binds every token unit to an exact number of satoshis. Deploy and mint are inscriptions; every later movement is an ordinary Bitcoin spend of the satoshis that carry the units.
