For builders

Indexer and builder guide

What it takes to reconstruct DUST-20 state correctly: strict parsing, deployment resolution, positional allocation records, and honest handling of the moments when the chain moves under you.

i

A balance is a service's view, not consensus

Bitcoin does not know what DUST-20 is. Every balance is one implementation's interpretation of the chain. That makes provenance — source, coverage, observation height — part of the answer, not metadata to be stripped.

The pipeline

Indexing DUST-20 means indexing state transitions, not page loads. Each stage below has a job it must finish before the next one can be correct.

What you need to read from

Two sources are required, and they must be cross-checked against each other:

  • Complete blocks with input values, output values and output addresses. Without input values you cannot build the satoshi range, and without it you cannot compute a single transfer.
  • Authoritative inscription data for inscription identity, content, genesis output and genesis offset. A mint is only valid if its inscription sits at offset zero of an output holding exactly the declared satoshis.

Verify the network, the genesis hash, block continuity and agreement between the two sources on every poll. Fail closed on a gap, a mismatch, a malformed response or an unavailable upstream. An empty result after a timeout is unavailable, never a verified zero balance.

The allocation record

A balance is the sum of allocation records. Each record must answer which output, which rule, which source, and what chain state produced its interpretation.

Illustrative allocation record 
{
  "outpoint": "<txid>:0",
  "tick": "dust",
  "amount": "91",
  "unit_sats": "546",
  "offset_sats": "0",
  "output_value_sats": "49686",
  "origin_inscription_id": "<inscription id>",
  "owner_address": "<address>",
  "status": "confirmed",
  "observed_height": 0,
  "source": "your-indexer-id"
}

An implementation-facing shape, not a standardized public API. The requirement is traceability: a client must be able to recheck how the amount was derived.

Propagation algorithm

This is the core of a DUST-20 indexer. Everything else is bookkeeping around it.

  1. Skip coinbase transactions.
  2. Walk the inputs in order, accumulating a running satoshi total. For each input, look up any allocations on that outpoint. An allocation's span in the combined input range is [running_total + offset, running_total + offset + amount × unit_sats).
  3. If no input carries an allocation, there is nothing to do.
  4. Mark every contributing outpoint spent.
  5. Walk the outputs in order, accumulating a second running total, to give each output a span [start, start + value). Resolve each output to an address; an output you cannot attribute is unsupported.
  6. For each allocation, intersect its span with each output span. Skip unsupported outputs. Within the intersection, compute the first whole unit boundary at or after the intersection start and the last whole boundary at or before its end. The units between them survive, at a new offset inside that output.
  7. Anything not accounted for is burned: burned = amount − surviving.
  8. Emit a transfer effect only where the owning address actually changed. Same-owner movement is a split or merge, not a transfer.
first = ⌈(∩start − span_start) / unit_sats⌉ last = ⌊(∩end − span_start) / unit_sats⌋ Units surviving in an output = last − first, when positive. Use exact integer division; a float here loses satoshi precision and produces wrong balances.
!

Conserve, then verify

Assert surviving + burned = input_units for every allocation, every time. An unexplained satoshi difference is a defect in your implementation, not a rounding artifact to be tolerated. Treat it as a failure and stop.

The transaction visualizer runs exactly this algorithm in the browser, and conformance.json publishes the scenarios you can test against.

Chain instability

Reorgs and replacements are product states, not rare edge cases. They must be designed for, because they directly affect what a wallet may safely spend or list.

Reorganizations

Emit invalidations newest first. Reverse ledger mutations, restore allocations that had been marked spent, remove allocations the orphaned branch created, then replay the replacement branch. Track block association so this is possible at all.

Replacement and double-spend

A replaced transaction can have a different output layout, so it can burn units the original preserved. Mark affected pending allocations invalid or uncertain — never retain the old interpretation as spendable.

Mempool

Coverage of unconfirmed state is partial: there is no exhaustive feed with a stable pending lifecycle and disappearance handling. Label pending state as such and never let it back an irreversible decision.

Finality

The protocol defines no confirmation threshold. Publish your own finality depth, expose confirmation counts, and recompute derived state when the chain moves.

API expectations

No canonical DUST-20 indexer API exists. Consumers should treat any remote response as a contract that needs schema validation and an explicit source policy.

AreaExpectationFailure mode it prevents
Reads Return source identity, coverage level, observation height or time, pagination and a state label alongside the data. A bare array that cannot say whether it is complete, fresh, or from the source you think.
Errors Differentiate unavailable, malformed, stale, invalid-request, not-found and contradictory-state. A client interpreting every failure as an empty balance, then letting a user spend against it.
Near signing Revalidate selected outpoints at build time and return the height or timestamp the decision was made at. Building against an output that was spent while the page was open.
Coverage State plainly whether coverage is complete, partial or unavailable, and for which asset classes. Silently presenting partial mempool coverage as a full picture.
Versioning Version the response shape, or expose the uncertainty explicitly. A schema change breaking consumers with no signal that anything changed.

Before you ship a flow to users

  • Deploy and mint conformance fixtures cover valid and invalid field combinations, exact arithmetic and real output values.
  • Transaction fixtures assert selected inputs, recipient outputs, colored change, cardinal fee funding and ordinary change — including the constructions that burn units.
  • Conservation is asserted on every allocation transition, and a mismatch fails the build.
  • Reorg, replacement, stale-listing and indexer-outage behaviour is tested, not assumed.
  • Any workflow that could expose private key material is removed or independently security-reviewed.
  • Operators have rehearsed the stop, diagnose, communicate and re-enable sequence with redacted evidence.
