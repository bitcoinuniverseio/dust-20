How it works

How DUST-20 works

Six stages, one idea: a token unit is a fixed-size piece of bitcoin, and everything that happens to that bitcoin happens to the unit.

The lifecycle

Two of these stages are messages written into inscriptions. The rest are things that happen to ordinary Bitcoin outputs.

DEPLOY

Fix the rule

An inscription declares a ticker, a maximum supply, the exact satoshis backing one unit, and the total backing those two numbers imply. From this moment the satoshi ratio is permanent — no later message can change it.

MINT

Create units

An inscription claims an amount of units and states the satoshis backing them. It is only valid if that number equals amount × unit size and the Bitcoin output carrying the inscription holds exactly that many satoshis, with the inscription at offset zero.

HOLD

Own the output

The units now live in an unspent output you control. Your balance is the sum of the allocations across your outputs — there is no account anywhere that records it.

SPLIT

Divide the allocation

Spending the output lets you send some units to someone else and keep the rest. The split happens in satoshi space: each output takes a contiguous stretch of the input satoshis.

CHANGE

Catch the remainder

Units you did not send need an output big enough to hold them, positioned so each unit fits whole. If no such output exists, those units cease to exist.

INDEX

Observe the result

Indexers replay the chain, apply the rules and publish balances. Their answer is an interpretation of Bitcoin, complete with a source, a coverage level and an observation height.

Anatomy of a DUST-20 UTXO

A DUST-20 output is an ordinary Bitcoin output. What makes it a DUST-20 output is an allocation: a record that a specific stretch of satoshis inside it represents a number of units of a ticker.

PartWhat it isWhy it matters
txid:vout The outpoint — which output this is. The unit of ownership. Spend it and every unit inside moves.
value The output's satoshi amount. Must be large enough to hold the allocation. For a mint it must equal the declared sats exactly.
offset Where the allocation starts inside the output, in satoshis. Usually zero, but after a split it may not be. Without it the next spend cannot be computed.
tick + unit_sats Which deployment the allocation follows. Fixes how many satoshis one unit occupies, and therefore where unit boundaries fall.
amount How many whole units the allocation represents. Always a whole number. DUST-20 balances have zero decimal places.
i

An output can hold more satoshis than its allocation needs

81 units at 546 satoshis occupy 44,226 satoshis. An output of 50,000 satoshis can carry them comfortably — the extra 5,774 satoshis are just ordinary bitcoin sitting in the same output. What matters is that every whole unit fits inside.

The arithmetic

There are only two formulas to learn, and both must hold exactly. Implementations use exact integer arithmetic throughout: satoshi values routinely exceed the range a 64-bit float can represent without loss.

max_sats = supply × unit_sats A deploy's total backing is its supply multiplied by the satoshis behind one unit. Example: 1,000,000 units × 546 sats = 546,000,000 sats.
sats = amt × unit_sats A mint's declared backing is the units it creates multiplied by the unit size — and the Bitcoin output must hold exactly that. Example: 100 units × 546 sats = 54,600 sats.

Both are redundancy checks. The value could be computed rather than declared, but stating it lets a reader catch a builder that used the wrong unit size or lost precision to floating point. A payload that is off by a single satoshi is rejected, not corrected.

Try it in the playground — change the supply or unit size and watch the derived values update with exact integer arithmetic.

Two kinds of satoshi

Every DUST-20 transaction involves two categories of bitcoin that must never be confused.

Colored satoshis

The satoshis carrying token units. They are conserved: every one that reaches a supported output keeps carrying its unit. They must never be used to pay a fee, because a satoshi paid to a miner takes its unit with it.

Cardinal satoshis

Ordinary bitcoin carrying no units. This is what pays the miner fee and provides ordinary change. A correctly built DUST-20 transaction always includes a cardinal input for exactly this purpose.

!

The fee is not part of the token arithmetic

The miner fee is whatever the transaction does not pay out. If you shrink a colored output to make room for a fee, you have not paid the fee out of "spare" value — you have moved the boundary of the colored range and probably destroyed units at the end of it.

How units follow satoshis

This is the rule that decides everything about a transfer. It is worth reading twice.

  1. Lay every input value end to end to form one long satoshi range.
  2. Lay every output value end to end to form a second range, in output order.
  3. An allocation occupies a contiguous span in the input range. Each unit is a block of unit_sats satoshis inside that span.
  4. A unit survives only if its whole block lands inside a single supported output.
  5. Everything else is burned.

Three consequences follow directly, and each one has burned real balances:

Output order matters

Moving an output changes which satoshis land where. Reordering outputs is never cosmetic — it can move your entire allocation into the wrong place.

Fees eat the tail

The fee is the satoshis past the last output. Units sitting in that region are destroyed, which is why the fee must be funded by a cardinal input.

Partial units vanish

A unit straddling an output boundary does not round up or split. It simply does not survive.
