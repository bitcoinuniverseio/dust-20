    Reference

    Protocol reference

    Every operation, field, formula and rule, each labelled with where it comes from. Where the legacy specification and the current implementation disagree, both positions are stated and the difference is explained rather than hidden.

    VERIFIED

    Documented in the legacy DUST-20 specification and enforced by the Bitcoin Universe production indexer.

    Operations

    DUST-20 uses inscriptions for exactly two operations. Movement and destruction are consequences of ordinary Bitcoin spends, not messages anyone writes.

    Field ledger

    Each operation declares an exact key set. A payload carrying an unknown field, or missing a required one, is rejected outright — it does not degrade to a warning.

    Formulas

    All arithmetic uses exact integers. Satoshi values routinely exceed what a 64-bit float can hold without loss, so an implementation using doubles will silently produce wrong results at scale.

    Rules

    Constraints that span more than one field, covering the reader profile, deployment resolution, mint placement, transfer semantics and indexer behaviour.

    Where sources disagree

    This is the part of the documentation that matters most for anyone implementing DUST-20. Earlier versions of these docs listed several of these as unreconciled compatibility splits. The current production implementation answers most of them — but it answers them as one implementation, not as a ratified standard.

    Open questions

    These have no authoritative answer. They are documented as open rather than filled in with a plausible-sounding rule, because a wrong guess here destroys balances.

    DUST

    DUST-20

    DUST-20 binds every token unit to an exact number of satoshis. Deploy and mint are inscriptions; every later movement is an ordinary Bitcoin spend of the satoshis that carry the units.
